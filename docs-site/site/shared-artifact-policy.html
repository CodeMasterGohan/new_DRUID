Shared artifact & model policy

The offline-first model and artifact policy shared by new_DRUID and New_sage. Grounded in the specs and the artifact manifests at services/artifacts/manifests/ in each build tree.

The offline-first rule

Production services load only pre-staged artifacts from the internal registry. They fail startup rather than downloading anything at runtime. There is no network fetch path in production — missing artifacts are a hard startup error, not a fetch.

Artifact manifests

Every approved artifact has one YAML manifest (one per model, plus New_sage's seed-corpus manifest). A manifest records:

  • artifact_name — e.g. allenai/olmOCR-2-7B-1025-FP8
  • upstream_source — the canonical HTTPS origin (Hugging Face or ghcr.io)
  • upstream_revision — an immutable pin (commit hash / image digest). Branch-style revisions (main, master, latest, stable, dev, develop, head) are rejected.
  • internal_location — where the staged artifact lives on the box (/models/... or /artifacts/...); this is the source of truth for the verifier.
  • license — every approved model and dependency needs a recorded license.
  • files — per-file sha256 checksums.
  • approval_record — the signed approval ID.

Template entries (zeroed sha256 values, <immutable-commit-hash> placeholders) are only acceptable during drafting. They must be completed during controlled staging before the manifest is approved.

Prohibited sources

Downloads from the following — or from any other unapproved endpoint — are prohibited:

  • modelscope.cn (and subdomains)
  • hf-mirror.com, hf-mirror.aliyuncs.com
  • any Chinese mirror repository
  • any host not on the staging allowlist

ghcr.io is allowlisted only for the DevDocs image. The staging validator enforces this (artifact_manifest.py: DEFAULT_PROHIBITED_HOST_PATTERNS), rejecting prohibited hosts and non-HTTPS sources at manifest validation time.

Staging workflow (summary)

  1. Validate manifest — source allowlist, HTTPS scheme, immutable revision.
  2. Verify checksums — every file's sha256 under the artifact root must match the manifest.
  3. Mount — the registry is mounted read-only into the service containers.
